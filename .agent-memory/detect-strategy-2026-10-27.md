# sniff 通讯参数自动识别：为什么慢 + 下一步怎么快（2026-10-27）

## 前提纠正（我一开始搞错了）

**sniff 档的通讯参数用户不配置。** sniff 没有持久槽是刻意的设计
（README「sniff 没有持久槽，这是刻意的」），参数完全靠设备自己认出来。

所以"用户配的参数被忽略""已知参数优先"这类方案**前提就不成立**，别再往那个
方向想。我第一版分析里写了这一条，是错的，已作废。

## 现状：串行盲扫 21 个候选

```
外层 parity {8N1, 8E1, 8O1}          ← 奇校验排第三层
  内层 baud {9600,19200,38400,115200,4800,2400,1200}
每候选 = uart.close + wait500 + uart.setup + 静默监听 DETECT_WIN_MS
```

命中判据：`stat.frames` 增量 > 0（收到 **CRC 合法**的帧）。

现场（用户总线：外部主站每 ~500ms 轮询一次；设备为 **4800 奇校验**）：

```
进 sniff
 ├─ 固定空等 5s                      mon.lua 的 sniff_wait(5000)
 ├─ p=0 (8N1)  7 baud × 2.5s = 17.5s  ← 全落空
 ├─ p=1 (8E1)  7 baud × 2.5s = 17.5s  ← 全落空
 └─ p=2 (8O1)  9600→19200→38400→115200→【4800】命中 = 12.5s
                                       合计 ≈ 52.5 秒
```

**奇校验 + 4800 恰好排在第 32 位。**

## 12-fix-2 做了什么

| 项 | 改前 | 改后 |
|---|---|---|
| 每候选耗时 | 0.5s + 2.0s = 2.5s | 0.5s + 0.8s = 1.3s |
| 首等（UART 稳定） | 5s | 2s |
| 4800 奇校验命中 | ≈52s | ≈27s |
| 轮次之间 | 整个 21 候选重扫 | 跳过已试过的，不重扫 |
| 识别过程可见性 | 全黑盒，只有转圈 | `R:STAT` 的 `mode.mon.try_baud` / `try_parity` |

1. `DETECT_WIN_MS` 2000 → **800**（`core/config.lua`）
2. `DETECT_SETTLE_MS` = **2000**（新配置项，替掉硬编码的 5000）
3. **候选记忆**：mon.lua 的 `tried` 表（key = `"baud:parity"`）
   - ⚠️ 只在 `mon.start()` / `mon.restart_detect()` 清零
   - ⚠️ **不在 `request_detect()` 清** —— 它也被 `cmd.lua` 的 `R:AUTODETECT`
     轮询路径调用（前端每秒轮询一次，见 `frontend/renderer/app.js` 的
     `pollDetect`），那里清了就等于每轮从头扫，记忆白做
4. `stat.rx_bytes` 计数器 + 每个候选日志打 `frames=N bytes=M`
5. `R:STAT` 暴露 `try_baud` / `try_parity` / `rx_bytes`

## 下一步（量完再改）：21 个候选 → 7 个

`stat.frames` 只在 **CRC 合法**时才 +1，所以"**这个 baud 上有流量、只是校验位
不对**"这个强信息被整个丢掉了。

**如果** UART 在 parity 错时**仍然把字节交上来**（一般 UART 只置 parity error
flag，不丢字节），那么：

1. 先用"收到过字节"在 **7 个 baud** 上定位 baud（每个短窗口）
2. 再在该 baud 上用 CRC 找出正确的 parity（3 个）

→ 21 次降到 10 次，总耗时 ~6s。

**但这个假设没在设备上验证过**，所以 12-fix-2 先把 `bytes=` 打进日志。

### 下一轮看日志要确认什么

跑一次 sniff，把识别阶段那几行 `check baud=... frames=N bytes=M` 贴回来：

| 观察到的 | 结论 |
|---|---|
| 某个候选 `bytes>0` 且 `frames=0` | ✅ parity 错时字节收得到 → **可以上 7 候选方案** |
| 所有候选 `bytes=0`（除了命中的那个） | ❌ parity 错时字节被 UART 丢了 → **这条路走不通**，得换思路（按主站轮询周期反推 baud？或者让用户手填？） |

## 另一条没做的路（要用户拍板）

**跨会话记忆"上次认出来的 (baud, parity)"**：第一次 27s，之后 1.3s。
需要 fskv 落盘一个 key —— 与"sniff 不落盘"的设计原则有张力。
用户 2026-10-27 明确选了"只做第 1 步"，这条**没做**。

## 顺带：内存

同一次现场测试暴露了 sniff 档 Lua 堆水位问题（详见
`.agent-memory/uart-release-and-stall-2026-10-27.md`）：

- 12-fix 之后满负荷实测峰值 **236KB**，越过 ~231KB 的崩溃线
- 基线从 198KB 抬到 221KB 的原因是 `dataCache` 填满 128 条（**到顶就不再涨**）
- 12-fix-2：插桩真删掉（改从 `R:STAT` 的 `iot.lua_kb` 看）+ 拓扑重建节流 5s

## 口径备忘

- `os.clock()` 是**秒**级单调时钟（项目统一口径）。配置里凡是毫秒，
  比较前**必须除 1000** —— 12-fix-2 就先写错过一次（5000 秒 = 83 分钟）。
- `rtos.meminfo("sys")` **不是** Lua 堆（实测差 3 倍）。
  判断"Lua 堆还剩多少"只能用 `collectgarbage("count")`。
