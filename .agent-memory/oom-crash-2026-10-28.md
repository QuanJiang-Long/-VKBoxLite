# sniff 档 OOM 崩溃复盘（2026-10-28，12-fix-3 / 12-fix-4）

## 现场

用户用**多寄存器**设备测 sniff 上报（不是上次那种单寄存器场景），跑到 130 秒崩了：

```
E/mem memory allocation failed total 307192, used 266752, alloc 3033
D/user.cmd tx: RET:FAIL:handler error:not enough memory
W/user.iot build_items failed, skip publish: iot.lua:290: not enough memory for buffer allocation
W/user.iot topo_sig failed, skip this round: iot.lua:459: not enough memory for buffer allocation
E/user.coroutine.resume not enough memory
stack traceback:
	mbus.lua:188: in function 'mbus.parse_value'
	mon.lua:210: in upvalue '?'
	mon.lua:239: in function 'mon.pick_dtype'
	mon.lua:290: in upvalue '?'
	mon.lua:341: in upvalue '?'
	mon.lua:402: in function <mon.lua:395>
E/main Luat: not enough memory
E/main Lua VM exit!! reboot in 15000ms
```

**崩溃点不在上报路径** —— `topo_sig`/`build_items` 都被 pcall 兜住，只打
"skip this round"。真正 fatal 的是**收帧处理协程**（`mon.lua:402` → `process_frame`
→ `push_rsp_value` → `pickDtype` → `mbus.parse_value`）。

`used` 一直在 **258840~268696** 之间波动、**从不降到 253KB 以下**。堆总量 300KB，
空闲 40KB 却申请不到 3KB 连续块 = **碎片化 + 常驻太高**。

## ⚠️ 走过的弯路（重要，别再走）

我一度判断那 253KB 地板是「Lua GC 的触发水位」：以为 Lua 5.3 默认
`GCpause=200`（活对象翻倍才完整回收），活对象 ~126KB 时地板正好 ~253KB，
于是打算用 `collectgarbage("setpause", 120)` 压下去。

**单测把这个否掉了**（`tests/lua/test_gc_pressure.lua`）：

- LuatOS 的默认 pause 是 **90**，不是 200；
- setpause 的值**存得住**（读回旧值确认），但把 pause 调成 120 / 200，
  垃圾水位峰值**纹丝不动**（238.2 vs 238.3 KB）。

**所以 253KB 地板就是活对象本身**，调 GC 参数救不了 OOM。**只能少常驻、少分配。**

> 教训：别把"听起来合理的 GC 理论"直接写成代码。先用单测在 PC 仿真器上量一把
> （LuatOS 仿真器就是设备同款 Lua 5.3 内核，量得准）。

## 第二次崩溃（12-fix-4）：碎片化，不是活对象

12-fix-3 提交后（推断表 512→128、dtypeHistory 封顶、parse_value 零分配），
现场又跑 5 分钟，还是崩了 —— 但**崩点变了**：

```
E/main iot.lua:621: not enough memory for buffer allocation
stack traceback:
	[C]: in field 'concat'
	iot.lua:621: in upvalue '?'      <- send_meta 里 table.concat 拼 600 字节
	iot.lua:1737: in function <iot.lua:1659>
```

`used=275456 / total=307192` —— **还剩 31KB 空闲，却切不出 600 字节连续块**。

**这不是活对象太多，是【碎片化】。** 根因是**分配速率**：

| 每秒都在做的事 | 分配量 |
|---|---|
| `publish()` 一次（重建配置 + 拼 ~4KB body + MQTT 编码） | ~12KB |
| `build_nodes()` 一次（每 5 秒） | ~14KB |
| `meta_sig()` 一次（含 csq → 信号强度一变就重发元数据帧） | ~2KB |
| `collector.push_data` 80 次/秒，每次 `string.format` 一条进**没人读的** ring | ~5KB |

现场实测 `published` 从 112 涨到 213：**126 秒发了 101 次 = 0.8 次/秒**。

**修法 = 统一上报调度（`lua/iot/pubsched.lua`）**，用户拍板最小间隔 30 秒。

## 三处根因（子 agent 全量审计 + 我的崩溃堆栈分析）

### 1. 推断表 —— ~140KB 常驻 + ~185KB 瞬时

- `mon.lua` `MAX_INFER_ROWS = 512`，每行是一张 **9 字段 table**（56+9×24 ≈ 272B）
  → 512 行 ≈ 136KB
- **而且 `infer()` 的产物被模块级 local `infer_cache` 整份留在内存里** ——
  README 一直把它记成"临时分配"，漏了它是**常驻**
- 重建那一瞬间还要额外吃 agg 哈希 + `"slave:reg12345"` key 串 ≈ 185KB
  → **正好能在收帧协程申请 3KB 时把池子打碎**，与崩溃堆栈完全吻合
- 512 这个数是 2026-10 为防"qty 展开成几万项"定的，但那件事已经由
  `util.clamp_qty` 单独挡住了 → **降到 128**（下游 `node_json` 的 `MAX_PROPS`
  才 64，128 已 2 倍余量）

### 2. `dtypeHistory` —— 全项目唯一真正没有硬上限的常驻结构

- 每个见过的地址一条 alias（FIFO 深度 5），只在 `mon.start()` 整表清空
- **`mon.stop()` 不清**，`dataCache` 淘汰时也不联动
- 估算每 alias ≈ 200B：128 地址 ≈ 26KB，512 ≈ 100KB，2000 ≈ 400KB（单这项就爆）
- 而 `dataCache` 那边是封顶 128 的 —— **同一批地址，只有 dataCache 有上限，
  这个不对称就是缺口**
- 修法：`MAX_HIST_ALIAS = 128`（与 dataCache 对齐）+ `mon.stop()` 补
  `clear_history()`

### 3. `mbus.parse_value` —— 每秒约 1.1 万次分配

- 原来每次调用分配：`raw` 字符串（`data:sub`）+ `b` 表 + （word_swap 时）第二个表
  + （float 时）第三个表 = **2~4 个对象**
- 而 `pickDtype` 一次就调它 **8 次**（int16/uint16 + int32/uint32/float32 ×
  word_swap 两种）
- 一个 30 寄存器的响应帧 → ~120 次 parse_value → **~240 次分配/帧**
- 现场 `stat.frames=6173` / 130 秒 ≈ **47 帧/秒** → **每秒约 1.1 万次分配**
- 修法：改成 `data:byte(p+1, p+8)` 一次取 8 个字节（多返回值走栈），
  中间一律不建表 → **零分配**
  ⚠️ 语义必须逐字节一致 —— `tests/lua/test_dtype_band.lua` 走 `mon.pick_dtype`
  端到端验（含 float32 字交换 / int32 千万级惩罚），改完跑一遍就知

## 另外两处降 churn（不是崩溃主因）

- **`cfg.lua` 配置解码缓存**：`load_poll`/`load_pull`/`load_alias` 每次调用都要
  `fskv.get` 整份 JSON + `json.decode` 整张表（128 条 ≈ 35KB 垃圾/次），
  而 `build_items()` 一次调用里反序列化 3~4 遍。
  → 只缓存**解码后的原始表**（归一化仍每次跑，各调用方拿各自独立的一份，
  改它不会串味 —— 这点重要，`poll.lastCfg` 长期持有 `load_poll()` 的结果）
  → `build_items()` 里 `alias_map(c)` 复用已加载的配置（3 次 → 2 次）
  ⚠️ **写盘必须让缓存失效**：`kv_set` / `reset_user` / `clear_pull`
  ⚠️ **声明必须在使用之前**：`local json_cache` 晚声明的话，`kv_set` 里那次
  `json_cache[k] = nil` 会写到**全局表**上，缓存永远不失效 —— 我第一版就写错了

## 12-fix-4 的设计要点（统一上报调度）

用户拍板：**最小间隔 30 秒**、**csq 从元数据指纹里摘掉**、**先加结构普查**。

- 新模块 `lua/iot/pubsched.lua`，三个通道 `meta` / `prop` / `topo`
- 口径：**"内容变了"= 事实（只置脏）；"该不该发"= 策略（走闸门）**
- 闸门按**上次【尝试】**计时，不是上次成功 —— 发送失败（多半 OOM）时
  不要每秒重试，重试本身又是一份垃圾，会把堆压得更碎
  ⚠️ 这条我在实现时踩过：兜底路径原来用 `last_os`（上次成功），
  失败重试时它不更新 → 兜底每秒都触发 → 白改
- `ready(ch)` 给"内容变了要靠重建才能知道"的通道用（拓扑）：
  想知道寄存器集变没变得先重建，而重建本身很贵 → 按时间闸门，不每轮重建
- `reset()`（重连时调）把各通道**置脏**而不是清脏：重连后要重新报一遍。
  ⚠️ `st.wall` 设成"现在"而不是 0 —— 否则 interval_s 兜底会在重连那一刻
  空转一次（没什么可发的，白白 build_items 一次）

## 没做的（评估过，风险/收益不划算）

- **只发变化的点**（而不是每次重发全部 128 个点）—— 收益最大，但需要平台
  协议确认：property-post 能不能只带一部分属性？没确认之前不动。
- `collector.dataCache` 每条存整帧 hex（U4 上报不用）—— 省 5~10KB，但要动上报
- `mbus.decode_frame` 的 `raw`/`data`/`hex`/`vhex` 四份同源大串 —— 省 8~10KB
- `S.pull.result` 的 `skipped` 明细无上限 —— sniff 档不触发（平台推空快照）

## 第三次崩溃（12-fix-5）：churn 是碎片化的根源，代码本身占 276KB

12-fix-4（统一上报调度）烧上去之后，现场又崩了两次。**崩溃点从上报路径挪到了
收帧路径**，而且两次都紧跟着用户打开前端「总线报文」面板（`R:FRAMES=30`）：

```
E/mem memory allocation failed total 307192, used 282488, alloc 3471   <- 3471 = R:STAT 的 JSON
E/mem memory allocation failed total 307192, used 276112, alloc 1568
E/user.coroutine.resume not enough memory
  mbus.lua:218 (parse_value) <- mon.lua:244 <- mon.lua:273 (pick_dtype)
  <- mon.lua:324 <- mon.lua:375 <- mon.lua:436
E/main Luat: not enough memory -> Lua VM exit!! reboot in 15000ms
```

`used 282488/307192` = 已用 92%，**还剩 24KB 却切不出 3.4KB 连续块** —— 碎片化。

### 根因一：我们的代码本身占 276.5KB（堆的 92%）

`tests/lua/test_heapsize.lua`（新写）：在 PC 仿真器里逐个编译 `lua/` 的模块、
留住产物、量 `collectgarbage("count")` 增量。

| 模块 | KB | 模块 | KB |
|---|---|---|---|
| iot/iot.lua | 73.1 | iot/pullcfg.lua | 11.6 |
| bus/mon.lua | 33.1 | sn/sn.lua | 10.7 |
| svc/cmd.lua | 22.6 | util.lua | 10.4 |
| bus/poll.lua | 21.6 | iot/mqttcfg.lua | 9.5 |
| bus/mbus.lua | 16.2 | lbsLoc2.lua | 8.2 |
| cfg.lua | 13.5 | 其余 7 个 | 34.6 |
| sn/prov.lua | 13.1 | **合计** | **276.5** |

- 设备上 idle 档 `collectgarbage("count")` = **190KB**，堆总量 300KB
  → **留给运行期数据的只有 ~110KB**
- **去注释对体积毫无帮助**（burn 版 275.75 vs 仓库版 273.46 KB）：编译产物体积
  由指令和常量决定，注释不进产物。`prep_burn.ps1` 只省 flash，不省 RAM。
- `test_heapsize.lua` 把 320KB 钉成红线

### 根因二：churn ~110KB/秒（碎片化的来源）

`tests/lua/test_churn.lua`（新写）。**量法有个坑**：
Lua 5.3 的 `collectgarbage("stop")` **只关紧急回收，增量 GC 照跑** ——
"跑 N 次看 count 增量"量到的是**净增长**（GC 跟得上就是 0），不是真实分配量。
正确量法：让 N 次的分配量**低于 GC 启动阈值**（≈ 活对象 × 1.9），期间 GC 一次
都不启动，增量才是真实分配量。N=50 × 1KB = 50KB 远低于阈值，分辨率
0.1KB/50 = 2 字节/次。校准：noop 必须报 0、空表必须报 ~32 字节（32 位 Lua)。

改前 → 改后：

| 项 | 改前 | 改后 | 改法 |
|---|---|---|---|
| `mon.pick_dtype`（1 槽位） | 632 B | 29.5 B | 3 个候选表字面量写在函数体里 → 每次调用重建 8 张表；提到模块级常量 |
| `collector.push_data`（1 点） | 192 B | 16 B | 每次新建 7 字段表 → 老 key 原地改字段 |
| `mbus.decode_frame`（1 帧） | 450 B | 178 B | 帧表复用 + vhex 从 hex 切 + 闭包提到模块级 |
| 同一帧解两次 | ×2 | ×1 | `next_frame` 解一遍扔掉，`process_frame` 又解一遍 |
| 调试 ring | 176 format/秒 | 0 | 全项目没有读者 → `W:RING=1` 显式打开 |
| `R:STAT` | 3471 B | ~1800 B | iot 状态被**编码两遍**（iot 段 + mqtt 段一模一样） |
| `R:FRAMES` | ~9 KB | ~3 KB | 帧表里的 raw(二进制)/data 丢掉（JSON 里 raw 会转义成 \u00xx） |

**现场换算：48 帧/秒 × 1.7 槽位/帧，churn ~110KB/秒 → ~12KB/秒。**

### 顺带发现：`census` 那一行一直是瞎的

原来打 `collectgarbage("count") / 1024`，但 **LuatOS 这个接口返回的就是 KB**
（不是标准 Lua 的字节）—— 于是每行都打成 `lua=0.2KB`，现场看着像"堆才用了
0.2KB"，**白白误导了两轮排查**。设备上 `R:STAT` 的 `lua_kb`（直接取 count）
显示 190~231 才是真水位。现在 census 和 R:STAT 同一口径，并加
`fps=` / `push=` / `gc=`。

### 12-fix-5 的配套

- **堆水位保险丝**（`iot.lua` task_main，1 秒一轮，不在 UART 热路径）：
  水位 > 240KB 就 `collectgarbage("collect")`，最多 10 秒一次。
- **`W:RING=1` / `R:RING`**：环形调试缓冲改成显式打开。
- **`vhex` 从 `hex` 切**：帧结构固定（slave fc bc data(bc) crc2），
  载荷从第 4 字节起 = hex 串第 7 字符起，长 2*bc 字符。

### 还欠着的账

**276KB 的代码 vs 300KB 的堆** —— 12-fix-5 只压了运行期 churn，**代码体积
一分没少**。候选（都要用户拍板）：`bus/poll.lua`(21.6KB) / `bus/mon.lua`(33.1KB)
改成按需 require；`iot/iot.lua`(73.1KB) 拆常载/按需两半；`cfg.lua` / `lbsLoc2.lua`
能不能不常驻。⚠️ LuatOS 的 `require` 是运行时读 FS，但 `dep_graph.py` 是静态扫的，
改成懒加载要重跑依赖检查。

## 环境坑（顺手记一下）

**LuatOS PC 仿真器崩过一次之后，`%TEMP%\vkbox_lua_pc_test` 这个 staging 目录
就坏了** —— 之后跑**任何**测试（包括原本能过的）都会在第一行 print 之前


## 口径备忘

- `collectgarbage("count")` = **活对象 + 还没扫掉的垃圾**；`collect` 之后才是活对象
- ⚠️ **LuatOS 的 `collectgarbage("count")` 返回的是 KB，不是标准 Lua 的字节** ——
  拿它当字节用会差 1024 倍（`census` 那一行就栽在这上面，一直打成 `lua=0.2KB`）
- ⚠️ **Lua 5.3 的 `collectgarbage("stop")` 只关【紧急回收】，增量 GC 照跑** ——
  想量"真实分配量"不能靠它，要靠"N 次分配量低于 GC 启动阈值"
- `collectgarbage("step")` 是**增量**回收，不阻塞（实测 200 步能把 398KB 垃圾
  压到 53KB）；`collectgarbage("collect")` 是完整回收，**绝不能放热路径**
- `rtos.meminfo("sys")` 不是 Lua 堆（实测差 3 倍）
- Lua 的函数实参**先求值再调用** —— 想省一次分配，拼接必须写在 `if` 里面
- Lua 的**表字面量写在函数体里 = 每次进函数重建一张表** —— 热路径上就是
  每秒几百张（12-fix-5 的 pick_dtype 就是栽在这，632 字节/次）
- `os.clock()` = 秒级单调时钟（开机起算，不受 NTP 跳变）；`os.time()` = 墙钟
