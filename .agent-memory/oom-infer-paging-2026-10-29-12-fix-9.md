# 第五次现场复盘：推断表一页 8KB，切不出来（2026-10-29，12-fix-9）

> 结论先行：**又是"碎片化"，但这次不是 GC 不合并的问题，是"要一块 8158 字节的连续块"**。
> 池里全是小洞，8KB 的连续块根本切不出来 —— `alloc 8147 failed`。
> 这次的处理不是"再省点内存"，而是**别再要那块 8KB**（分页）+ **别再造那 50KB 瞬时垃圾**（B3）。

## 现场（09:14~09:19，SN VL20261019001）

```
E/mem memory allocation failed total 307192, used 290256, alloc 8158   ← 要 8KB 连续块
E/json json encode failed by memory less
E/json json encode out of memory!!!                                   ×4
RET:INFER={}                                                           ← 应答变空表
RET:STAT={"mode":{},...}                                               ← 状态也空了
E/uart system is out of memory!!!                                      ← 系统池见底
（09:19:03 整机卡死 + ramdump）
```

用户侧的现象：前端刷新出来 64 条参数，**再多就不出了**，再跑一会儿模块死机。

## 三个最容易读错的数字

1. **`total 307192` 是 Lua 堆**（不是"剩 307KB"）。`used 290256` = 池的 **94.5%**。
2. **`E/uart system is out of memory!!!` 是【系统池】**（`rtos.meminfo("sys")`，
   total 203040），跟 Lua 池是两回事。崩溃那次系统池 190780/203040 = **94%**。
   - ⚠️ **系统池没有泄漏**：同一份固件另一次跑，uptime 317s/327s/337s 的
     `mem=145708/154168/154204` —— 涨 8.5KB 后稳在 **≈154KB（75.9%）**。
     崩溃那次多出来的 ≈36KB 是**排队等发的 8KB 应答**（R:INFER 整表应答在
     uart tx 缓冲里排着）→ 分页把应答砍一半，这块也跟着减半。
3. **"64 条参数"不是上限**。`MAX_INFER_ROWS = 128`，`infer_clamped = 0`
   说明当时一条都没被截断 —— 64 是**总线上的真实地址数**，不是封顶。

## 12-fix-9 改了什么

| # | 改动 | 位置 | 省的是什么 |
|---|---|---|---|
| A | **分页**：`R:INFER=off,n`，一次最多 32 行 | `mon.infer_page` / `cmd.lua` | 峰值连续块需求 8158 → ~4000 B |
| B3 | **名字表外置**：行一个字段都不加，名字挂顶层 `names` 表 | `iot.attach_names` | 一次 R:INFER 少造 ~50KB 瞬时垃圾 |
| 腾挪1 | **dtype 历史打包成一个数**（每帧 1 个 16 进制位） | `mon.dtypeHistory` | 每地址常驻 −96 B |
| 腾挪2 | **数据点不再存 hex** | `collector.push_data` | 每地址常驻 −31 B |

配套：`iot.alias_map()` / `cfgstore.alias_map()` 加缓存（键 = 配置版本 + 槽位，
写盘时失效）→ 一次 R:INFER 少造 ~23KB 瞬时垃圾；`cmd.M.reply` 不再把整条应答
打进日志（大应答走 `reply_big`：一次 concat、只打长度 + 前 80 字节）。

### 一次 R:INFER 原来造多少垃圾（64 地址）

```
行复制(10 字段表)          23 KB
id/name 串                 28 KB
iot.alias_map()             8 KB
cfgstore.alias_map()       15 KB
load_poll/normalize 重建   15~20 KB
"RET:INFER=" .. json        8 KB
s .. "\r\n"                 8 KB
整条应答进 debug 日志        8 KB
                       ≈ 115 KB 短命垃圾/次
```

前端连点几下刷新，池就被这些短命垃圾打成碎片 —— 然后要 8KB 连续块就切不出来。

## 实测（PC 模拟器，`tests/lua/test_infer_mem.lua`，同一份量法）

64 个地址（累加器行 + dtype 历史 + 数据点）的**常驻**增量：

| | 64 地址常驻 | 每地址 |
|---|---|---|
| 旧 `13304dc` | 42.63 KB | **682 B** |
| 新 `12-fix-9` | **34.69 KB** | **555 B**（−127 B，−18.6%） |

## 教训

- **"池子快满了"和"崩溃"是两件事**：池子 95% 时，只有**要连续大块**的那条路
  会先死。别把余量当安全系数。
- **大应答的形状比大小更要命**：8158 字节不是问题，**"要一块 8158 连续的"**
  才是问题。分页把峰值需求砍一半，比省 10KB 常驻更管用。
- **名字这类"每行都一样形状"的东西不要挂到行上**：行字段数是 2 的幂闸门
  （8 字段 = 8 槽，第 9 个字段就 16 槽，203 → 363 B/行），名字应该挂到
  **顶层表**，用 key 关联。
- **PC 模拟器偶尔会崩（0xC0000005）**：先怀疑自己的暂存目录 —— 往
  `%TEMP%\vkbox_lua_pc_syntax\lua\` 里塞过临时文件之后，模拟器必崩；
  删掉整个暂存目录重跑就正常（脚本会自己重新拷模拟器）。
  另：PC 模拟器**没有 json 模块**（`require "json"` 会去找 lua/json.lua），
  所以应答字节数只能在设备上量。
