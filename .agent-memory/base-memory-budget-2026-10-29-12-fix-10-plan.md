# 现场复盘：池子 95% 的真正账本（2026-10-29，12-fix-10 的账）

> 结论先行：**这一轮没有崩（42 分钟 vs 上次 5 分钟），但设备是"瘸"的**：
> 拓扑一次都没发出去（topo=0）、U4 每次降级拆包、池子仍 95.2%。
> 更要紧的是：**128 个地址在当前固件下装不下，差 4.6%** —— 差的是**基线**，不是每地址成本。
> 所以下一步的第一件事是**降基线**（184 KB count = 池的 80%），不是继续抠每地址。

## 一、现场（2026-10-29 13:44:53 起，SN VL20261019001，82 个地址，跑了 42 分钟）

### 1.1 稳定的部分（好消息）

```
census lua=220.8KB points=82 rows=82 pub=261/0 aerr=0 err=0 fps=44~47
```
- `lua=` 三次采样纹丝不动（220.8 / 220.8 / 220.9）→ **没有泄漏**。
- 上次崩溃也不是泄漏，是**碎片化 + 峰值分配**。
- 系统池也稳：`mem=73316`(idle) → `109416`(30s) → `108920`(386s) ≈ 109KB/203040（54%）。
- `aerr=0`（没因分配失败丢帧）、`err=0`、`pub` 失败数 0。

### 1.2 瘸的部分（坏消息）

| 现象 | 根因 | 证据 |
|---|---|---|
| `topo=0`（拓扑一次没发出去）| `iot.lua:690` = 拓扑的 `table.concat(props, ",")`，64 个属性 × ~130 B ≈ **8.3 KB 连续块**切不出来 | `W/user.iot topo_sig failed, skip this round: iot.lua:690: not enough memory for buffer allocation`（每 30 s 一次）|
| U4 整包失败、降级拆成 4 块（25+25+25+7）| 82 点的整包 ≈3.9 KB 连续块切不出来 | `pub` 每 30 s **+4**（pub 数的是**消息条数**不是轮次）；`bfail` 每 30 s +2（U4 拆包 +1、拓扑失败 +1）|
| `E/mem ... alloc 2560 failed` 每 30 s 一次 | 同上，连续块申请失败 | 间隔正好 30 s（拓扑/上报的节奏）|

### 1.3 分页生效 ✓（12-fix-9 的直接效果）

```
R:INFER=0,32   → 3209 B      （旧路径整表 64~82 行 = 8158 B）
R:INFER=32,32  → 1770 B      （第 2 页，行字段少 → 更小）
RET:INFER_PUSH → 3254 B      （推的是当前页 ✓）
```
→ **"连续 4 KB 块"已经拿得到**，这正是以前要 8 KB 才崩的原因。

### 1.4 用户看到的"7 / 25 / 72 组上报"

- 7 组 = 刚开一会只有 7 个点有值。
- 72 组 = 那时 72 个点，一个包发完。
- **25 组 = 降级分包的一块**（`U4_CHUNK_PTS=25`，`iot.lua:56`）—— **这是碎片化的症状，不是设计的组数**。

## 二、最容易读错的数字

1. **`topo=0` 不影响 MQTT 连上**，但**平台没有物模型**（只发了 U4 的点）。
   "上报了部分数据"就是这么来的。
2. **`bfail` 的主要来源是拓扑**（每 30 s +1），不是 U4；U4 拆包要到 ~82 个地址才出现。
3. **`pub=261/0` 的 261 是消息条数**，不是发布轮次。
4. **`census lua=` 是 count（KB）**，池用量 ≈ ×1.33；`guard mem=` 是**系统池**，两回事。

## 三、账本：基线才是问题（这是 128 个地址装不下的原因）

从本轮开头的 census 直接算出斜率：

| 地址数 | lua= (count) |
|---|---|
| 0（idle，连上 MQTT）| **169.6 KB** |
| 0（刚进 sniff 档）| 201.8 KB（gc safety 那行，+32 KB）|
| 48 | 204.9 ~ 205.9 |
| 64 | 212.3 ~ 218.5（均值 215.5）|
| 76 | 218.4 ~ 218.7 |
| 82 | 220.8 |

- **基线（sniff 档，0 地址）≈ 184 KB count = 245 KB 池 = 池的 80%**
- **每地址 ≈ 450 B**（48→82：205.4→220.8 KB；区间 300~630 B）
- 池上限：307192 B = 300 KB = **count 231 KB**

```
理论地址上限 = (231 - 184) / 0.45 ≈ 104 个
128 个地址   = 184 + 128×0.45 = 242 KB count = 321 KB 池 > 307 KB  ← 超 4.6%
```
要 128 个地址成立，基线必须砍：
- 只算"装得下"：184 → **173 KB**（砍 11 KB）
- 算"拓扑还能发出去"（池 ≤ 85%）：184 → **133 KB**（**砍 51 KB**）

### 每地址 450~500 B 的构成（哈希表粒度是主因）

```
① mon.infer_acc[slave][addr] = {slave,addr,fc,hits,answered,dtype,conf,value}  ~230 B
② collector.dataCache[alias] = {addr,value,ts,dtype,conf,status}                 ~220 B
③ mon.dtypeHistory[alias]    = 打包数                                           ~24 B
④ alias 串 "reg123"（缓存的同一个串对象）                                        ~32 B
```
- ②的 value/dtype/conf/addr 与 ①**完全重复**；②的 conf/status **没有任何读者**
  （前端从 ① 拿 conf；U4 只用 value+ts；R:VAL 用 name/addr/value/ts/dtype）。
- ①的 8 个字段前端**全在用**（app.js:1374/1551/1604-1611），一个都不能删。
- 哈希槽按 2 的幂走：**≤8 字段 = 8 槽 = 203 B；第 9 个字段就 16 槽 = 363 B**。
  → 想省内存只能**少建表**或**改成列式数组**（数组段 16 B/元素）。

## 五、教训

- **"不崩"不等于"能用"**：`topo=0` 这种静默降级比崩溃更难发现 —— 要看 `topo=`/`meta=` 这两个计数。
- **基线 > 每项**：300 KB 的池，基线就吃了 245 KB。任何"再多支持 N 个地址"的需求，
  先问"基线能不能砍"，而不是"每地址能不能再省 50 B"。
- **哈希表的 8 槽门槛**是 Lua 里的隐形税：一个只有 2 个字段的小表也要 203 B。
  → 要么合并，要么列式。
- **flash 存模型 ≠ 省内存**：读回来还得进 RAM（还要 decode 的瞬时开销）。
  flash 的真价值是**保活**（重启不丢模型）和"RAM 只留活数据"。
