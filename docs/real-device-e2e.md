# 真机全流程跑测

脚本：`tools/real_device_e2e.js`（驱动真实 Electron 界面，不是 mock）

它是"带着界面跑一遍完整用户旅程"的自动化：枚举串口 → 打开 → 读信息 → 切档 →
读配置 → 加测试点 → 存配置 → 导出 → 导入 → 读实时值 → 内存探针 → 网络/MQTT →
sniff 推断 → 切回空闲 → 还原现场。每一步都点真实按钮、走真实 IPC / 串口，
所以能抓到"固件和界面没对上"的那类问题。

---

## 1. 测什么 / 不测什么

| 覆盖 | 不覆盖（脚本管不到，见第 7 节） |
| --- | --- |
| 串口打开/关闭、115200 链路 | 485 电气层：A/B 极性、共地、终端电阻、线长 |
| R:INFO 设备信息 | 掉电后配置是否保留（要真的断电） |
| 档位互斥切换、切档复位 | 长时间跑的内存爬坡 / 看门狗复位 |
| R:CFG / W:CFG 读写、分片上传 | 平台侧是否真的收到 MQTT 报文 |
| 导出/导入 JSON 回环 | 多从站并发、总线冲突、异常帧 |
| R:VAL 实时值（需从站） | 采集精度/量程标定 |
| R:MEM 内存连续块 | 4G 信号弱网重连 |
| R:NET / R:MQTT（需 4G） | — |
| sniff 推断（需总线流量） | — |

---

## 2. 跑之前（现场清单）

1. 模组烧好本仓库固件，USB 口在设备管理器里是一个 `COMx`。
2. 没有别的程序占着这个口：SSCOM、组态软件、另一个本工具实例、上次没退干净的
   Electron。**被占用时脚本会在第 2 步明确报"打开失败"**。
3. 485 接线：A/B 不接反、共地；长线或多从站时加 120Ω 终端电阻。
4. 从站地址 / 功能码 / 寄存器地址，和设备里"手动配置"的表一致，否则第 11 步会
   SKIP（读不到值），这不是固件问题。
5. 前端依赖已装：`cd frontend && npm install`（只为拿 Electron 二进制）。
6. 分清开发版/发布版固件：`R:MEM` 有应答就是开发版（`_build_flag.lua` 为 `false`），
   它注册了全部调试指令并保留原始 hex。发布版内存会宽松一点，评估大配置余量时
   两种都该测一次（开发版能过，发布版就没问题）。

## 3. 跑

```powershell
# 推荐：脚本自己拉起应用（会自动设 VKBOX_DOWNLOAD_DIR，导出不会弹原生保存框）
node tools/real_device_e2e.js --port COM32 --launch

# 也可以用已经在跑的应用（记得它启动时带了 --remote-debugging-port=9333
# 和 VKBOX_DOWNLOAD_DIR，否则导出会卡在系统保存对话框上）
node tools/real_device_e2e.js --port COM32
```

常用开关：

| 开关 | 作用 |
| --- | --- |
| `--launch` | 自己拉起 Electron 并带调试端口 |
| `--debug-port 9333` | 调试端口（默认 9333） |
| `--download-dir D:\xxx` | 导出落盘目录（默认 `%TEMP%\vkbox_e2e_dl`） |
| `--no-write` | 只读巡检，不写设备配置 |
| `--read-only` | 完全只读：不写配置、不切档、不导入、不切空闲（第一次接陌生设备先跑这个） |
| `--no-restore` | 切完空闲不还原配置（默认会导回去） |
| `--expect-slave` | R:VAL 没值算 FAIL（产线验收） |
| `--expect-net` | MQTT 未就绪算 FAIL（产线验收） |
| `--min-max-block 4096` | R:MEM 连续块下限（大配置场景调高） |
| `--keep` | 测完不关应用，方便手动复看 |

退出码：`0` 全 PASS/SKIP，`1` 有 FAIL，`2` 脚本/环境问题（连不上调试端口等）。

> Windows 控制台如果中文乱码，先 `chcp 65001`。

## 4. 判定语义

- **PASS**：这一步的软件链路通了。
- **FAIL**：该过的没过，需要排查（第 6 节）。
- **SKIP**：依赖外部条件，条件不满足属正常：
  - 第 3 步：`R:SN=EMPTY`（设备没做产线烧写）——这一条按 **FAIL** 报，因为平台侧
    身份会变成 `"nil"`；只是它不影响 485 采集，可以继续往后跑；
  - 第 11 步：没有 485 从站应答；
  - 第 13 步：没插卡 / 未注网 / 无 IP；
  - 第 14 步：MQTT 未配或平台不可达；
  - 第 15 步：总线上没有报文（从站不主动说话、主站没跑）。
  - 第 16 步：设备本来就在空闲，验证不了"切档复位"。

产线验收用 `--expect-slave --expect-net` 把 11/13/14 的 SKIP 升级成 FAIL。

## 5. 脚本做的事（19 步）

| # | 步骤 | 关键判定 |
| --- | --- | --- |
| 0 | 页面就绪 | 不是 mock 模式（有 `window.serial`） |
| 1 | 枚举串口 | 列表里出现 `--port` 指定的口；等列表稳定再选，避免刷新竞态 |
| 2 | 打开串口 | `S.open === true`，状态栏显示端口名 |
| 3 | 读设备信息 | SN 非空；真机要求长度 ≥ 8（IMEI 空只记备注） |
| 4 | 读运行模式 | R:MODE 有应答 |
| 5 | 切 manual | 点卡片 → 自动点确认框 → 模式变为 manual |
| 6 | 读 485 配置 | 状态栏出现"配置已读取"；记录波特率/行数 |
| 7 | 准备测试寄存器 | 设备已有配置就沿用；空表才加 `1 / uint16 / A1` |
| 8 | 保存配置 W:CFG | 状态栏"配置已保存"；真机等 40s（分片上传） |
| 8b | W:CFG 峰值内存 R:CTRACE | 分阶段采样，峰值 ≥95% 直接 FAIL（离 OOM 只剩几十字节） |
| 9 | 导出 JSON | 落盘且能解析、寄存器非空 |
| 10 | 导入 JSON | 原生文件框被拦截并回填，导入成功 |
| 11 | 读实时值 | 表格里出现数值（需从站） |
| 12 | 内存 R:MEM | 最大连续块 ≥ `--min-max-block`（默认 2048B） |
| 13 | 网络 R:NET | status=1 且 ip≠`-`（需 4G） |
| 14 | MQTT R:MQTT | `stat.connected === true`（`ready` 只表示配置齐了，不代表连上） |
| 15 | sniff 推断 | `S.infer.total > 0`（整张对象固定 10 个键，不能用键数判） |
| 16 | 切回 idle | 切档成功 + R:CFG 里寄存器已清空 |
| 17 | 还原现场 | 用第 9 步导出的文件导回；**设备原本 0 个寄存器时跳过**（保持空闲） |
| 18 | 关闭串口 | `S.open === false`，状态栏"未连接" |
| 19 | 页面错误 | 过滤 CSP 警告后应为 0 条 |

第 12/13/14 步没有界面入口，直接走页面的 `sendCmd`（R:MEM / R:NET / R:MQTT），
这是刻意的：它们本来就是排障探针。

## 6. FAIL 排查表

| 现象 | 先看这里 |
| --- | --- |
| 第 1 步：列表里没有 COMx | 驱动没装好 / 换 USB 口 / 设备管理器里是不是"未知设备" |
| 第 2 步：打开失败 | 端口被别的程序占着（含上一个没退的 Electron）；`--keep` 之后要手动关掉再跑 |
| 第 3 步：SN 没读到/为空 | `R:SN=EMPTY` 就是产线没烧：用 `W:SN=<SN>` 烧写。不影响 485，但 MQTT 的 clientId 会成 `"nil"` |
| 第 5 步：没切到 manual | 看状态栏与 toast；platform 档切换会多问一次"清空平台配置"，脚本会自动确认 |
| 第 6 步：配置没读到 | 看状态栏文案；R:CFG 超时通常是串口被抢或设备在重启 |
| 第 8 步：保存失败 | 先看报错原文：`fskv.set 拒写 ... not enough memory` = 设备内存不够（大配置常见）；`腾不出接收窗口` = max 连续块不够；两者都见第 8 节 |
| 第 9 步：导出目录没文件 | 应用不是用 `VKBOX_DOWNLOAD_DIR` 启动的，原生保存框把流程挡住了 → 用 `--launch` |
| 第 10 步：导入失败 | 确认应用是 manual 档；检查导出的 JSON 是否被手工改坏 |
| 第 12 步：max 太小 | 碎片化或配置太大；重启设备后再看一次，还小就是配置规模超了 |
| 第 19 步：页面有错误 | 一般是前端真实 bug，把错误文本带回仓库 |

## 7. 必须人工补的三项

1. **掉电保持**：跑完第 8 步（配置已保存）后给设备断电 10s 再上电，
   确认 SN/配置/MQTT 凭证还在，且能自动进入上次的 boot_mode。
   脚本无法控制电源，这一步只能人做。
2. **485 电气层**：A/B 反接、缺共地、缺终端电阻都可能"能通但偶发 CRC 错"，
   软件层测不出来。多从站时用示波器/总线分析仪看波形更稳。
3. **平台端到端**：第 14 步只能证明设备侧 MQTT ready。
   报文是否真的到了平台、字段对不对，要在平台侧看一次。

## 8. 内存规模测试（真机专属）

脚本：`tools/mem_scale_e2e.js`

全流程脚本只测"1 个点能不能存"，但现场真正会出事的是**大配置**。这条脚本往设备里
依次导入 N 个寄存器（默认 1/8/16/32/60），每存一次读三个数：

- `R:CTRACE`：这次 `W:CFG` 的分阶段峰值（enter/gc/decoded/norm/freed/saved/done）；
- `R:MEM`：当前 Lua 池 used/total + 最大连续块 max；
- `R:CFG`：**存完再读一次，核对行数**（2026-11-18 起）。"存得下"和"读得回来"
  是两件事，只测保存会把可用上限算高。

```powershell
node tools/mem_scale_e2e.js --port COM4 --launch
node tools/mem_scale_e2e.js --port COM4 --sizes 1,8,16,32,60,96,128
```

收尾：设备原本有配置就先导出、结束再导回；原本空配置就切回空闲。
`--keep-config` 保留最后一个规模。

**为什么必须真机测**：模拟器的 Lua 池是 4MB，真机只有 ~300KB。真机基线（开发版
固件、空闲）就在 88% 左右，60 点配置会把池子顶到 97%~99%，`fskv.set` 要一块
961B 的连续块都可能拿不到 —— 这一步在模拟器上永远复现不出来。

一次实测（2026-11-17，开发版固件，`_build_flag.lua` 为 `false`，当时还没有读回校验）：

| N | W:CFG 峰值占池 | 存完 Lua 水位 | max 连续块 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 93% | 89% | 12288 | PASS |
| 8 | 93% | 90% | 12288 | PASS |
| 16 | 94% | 91% | 8192 | PASS |
| 32 | 95% | 93% | 6144 | PASS（已经很勉强） |
| 60 | 99% | 97% | 2048~6144 | **间歇 FAIL** |

60 点失败时的设备原话（用 CDP 抓的完整收发）：

```
W:CFINISH=5,{...}
  → RET:FAIL:CFG:分片5/5写入失败: fskv.set 拒写(共961B): not enough memory for buffer allocation
```

即"配置本身没问题，是提交时拿不到 961B 连续块"。固件侧已经改掉（写盘前用
`string.rep` 真分配探一次连续块、不够就丢解码缓存 + 两轮 GC、每段写完再 GC 一次），
改完 60 点**能从空闲档一次存进去**（峰值 97%）。

### 2026-11-18：加上"读回"之后，上限比想象的低

同一天用带读回校验的脚本又量了一轮，两个新结论：

1. **"存得下"≠"读得回来"**。`R:CFG` 要把整份配置编成一条 JSON：32 点约 2KB、60 点
   约 4KB，还要留 `json.encode` 中间的临时串。池子见底时旧固件的 `jencode` 兜底回
   `RET:CFG={}` —— 前端显示 0 行，用户以为配置丢了，**再点一次保存就把设备清空**。
2. 这条路的实际上限比"保存成功"低得多：

| N | 保存（W:CFINISH） | 读回（R:CFG） | 顺序连测 1→8→16→N | 单跑（先切空闲再存） |
| --- | --- | --- | --- | --- |
| 1 | OK | 1 行 | PASS | PASS |
| 8 | OK | 8 行 | PASS | PASS |
| 16 | OK | 16 行 | PASS | PASS |
| 24 | OK | not enough memory | **FAIL** | 通过（96%，余量 ~11KB） |
| 32 | OK | `{}`（旧）／失败（新） | FAIL | FAIL |
| 40 / 48 / 56 | OK | not enough memory | FAIL | FAIL |
| 60 | OK（空闲档） | 失败 | FAIL（`CBEGIN` 就要不到 1200B） | 保存过、读回失败 |

**现场口径**：这套开发版固件在这台 Air780（Lua 池 307192B、空闲基线 88~90%）上，
**稳定可用 ≈16~24 点**。24 点已经贴着边缘（存完 96%），32 点起会出现"保存成功、
刷新后表格是空的"。给客户的表建议 ≤16 点，留一半余量。

> 2026-11-19 更新（A0 之后）：这张表里"读回失败"那一列已经作废 —— 真机复测
> 16/24 点**存得进也读得回**，32 点起改成**保存阶段**就先失败。上限本身没变，
> 因为卡点从"读"挪到了"攒 60 行表本"。细节和数据见下面 11-19 两节。

> 为什么这么低：基线里主要是脚本代码本身（瘦身后 220KB 源码装进 307KB 的池子），
> 剩下的十几 KB 要同时装 [配置表 + 分片暂存 + 应答编码临时串]。
> 想往上走只有三条路：发布版（去掉 5 条调试指令 + TR 采样，约几 KB）、
> 配置读改写改成流式（不整表装卸）、或把寄存器行改成紧凑数组存（省 30~40% 表内存）。

> `RET:CFG={}` 这个坑已按 R:VAL 的老规矩修掉：`R:CFG`/`R:REG` 编码不出来现在回
> `RET:FAIL:CFG:<原因 池水位>`（回归测试 `tests/lua/test_cmd_cfgfail.lua`）。
> 修完**不会提高上限**，只是让失败说实话 —— 用户看到"内存不够"，而不是"配置没了"。

> 排查手段：`--sizes 60` 单独跑，连跑两遍（第二遍就是"设备里已有 60 点"的现场），
> 第一遍过第二遍失败 = 内存余量问题，不是配置/链路问题。

### 2026-11-18：读回路径改成"不重解 + 不整条编码"

上面那张表的根子只有两个，都在**读**这一侧（写侧 60 点已经能过）：

1. **写盘会把解码缓存作废**。`kv_set` 落盘后 `json_cache[k] = nil`，于是保存成功后的
   第一次 `R:CFG` 要重读 fskv、重解整张表；更贵的是随后 `normalize` 还会**再造一张**
   同样大的表（60 点约 12KB）。存完只剩 6.7KB，这一步必然失败。
   → `cfg.lua` 加了一份 `norm_cache`：只有 `save_xxx_norm`（也就是 `W:CFG` /
   `W:CFINISH` 提交走的那条路）在**写成功后**把刚提交的归一化表挂上去，`load_*`
   先查它，命中就直接返回。挂的是 poll 正在跑的那张表，不多占一个字节；
   作废点与 `json_cache` 完全同步（写盘、清槽、`W:CBEGIN` 的 `drop_cache`）。
   注意**只挂 norm 路径**：普通 `save_xxx` 的入参是原始表，挂进去等于把没归一化
   的东西当归一化用。
2. **应答是"整条 encode"**。`R:CFG` 要把 `{cfg,slot,src}` 一次编成 ~4KB 字符串，
   `R:REG` 要把 60 行整表编成 ~7KB，两处都要一块大连续内存。就算改成"先逐行编、
   再一次性发"，60 个小串加起来也有 ~7KB —— 还是攒不出来。
   → `cmd.lua` 把这两条应答改成**边编边发**（`tx_stream`）：一行一行 encode，
   凑够 512B 就写一次串口，峰值 = 一个发送缓冲，与点数无关。
   安全前提沿用原来的 `tx_frags` 结论：`uart.write` 是 C 调用不让出 CPU，
   段间没有 yield 点；收端按 `\r\n` 切行，分几次写对前端透明。
   失败语义：**一个字都没上串口**时照旧回 `RET:FAIL:CFG/REG:<原因 池水位>`；
   已经写出去一部分才失败，则补一个 `\r\n` 收尾并写日志（前端按解析失败重试），
   绝不把半张表当完整配置发。

回归测试：`tests/lua/test_cfg_shard.lua` 第 11 例（读回 0 分配、丢缓存后回 flash、
提交失败不拿 RAM 旧表顶）、`tests/lua/test_cmd_cfgfail.lua`（R:CFG 逐行/流式/如实报）、
`tests/lua/test_cmd_reg.lua`（R:REG 同样三条）。模拟器全流程 16 PASS / 5 SKIP / 0 FAIL。

| N | 保存 | 读回（A0 之后，待真机复测） |
| --- | --- | --- |
| 32 | OK | 待测（预期通过：读回不再分配整表） |
| 60 | OK（空闲档） | 待测（预期通过：峰值 ≈ 512B + 最大一行） |

> 还没动的第三处：`R:VAL`（读实时值）在 60 点时仍可能失败 —— 卡点不在编码，而在
> `collector.snapshot()` 本身就要新建一份 60 行的表（约 9KB）。要过这一关得让
> collector 支持逐行回调输出，属于下一步。

### 2026-11-19：A0 真机复测 —— 读回好了，卡点换到"保存"这一侧

烧 `4a8be50`（A0 快照）后真机实测（同一天、同一台机器、`--sizes 16,24,32,48,60` 顺序连测）：

| N | 保存 | 读回 | 结果 |
| --- | --- | --- | --- |
| 16 | OK | 16 行 | PASS（峰值 97%） |
| 24 | OK | 24 行 | **PASS（A0 之前这一档读回必然失败）** |
| 32 | **FAIL** | — | 第 2/3 片 `rx 丢弃, 请重发` |
| 60 | **FAIL** | — | 第 3/4 片 `解码结果为空 pool 306912/307192` |

手工按片发（每片之间插 `R:MEM`）看得更清楚：

```
CBEGIN → max:2048 used:287208
片1 1177B OK → used 293488 max 2048
片2 1134B OK → used 298288 max 1024
片3 1134B → not enough memory        ← 60 行还没攒够, 池子已经没了
```

**根因不是碎片，是算术**：manual 档基线 **287K**（其中 14.8KB 是 `bus/poll` 加载进堆），
而每点常驻约 **530B** = 寄存器行哈希表 330B（5 字段 8 槽）+ 轮询 plan 70B + 采集缓存 130B。
60 点 ≈ 33KB，池子只剩 20KB —— 就算上传能塞进去，起轮询时还要再建 plan，必然崩。

同时发现一个白背的 23KB：`bus/mon`（嗅探模块，23.3KB 源码，实测加载进堆约 23KB）
被 `main.lua` / `bus/ctrl` / `svc/cmd` / `iot/iot` **四处顶层 `require`**，于是
manual/platform 档（从头到尾不碰嗅探）一直背着它。开机 idle 273K、进 manual 287K 里都有它。

### 2026-11-19：`bus/mon` 改成惰性加载（先摘掉这 23KB，再谈行压缩）

改法与 12-fix-8 给 `bus/poll` 做的一模一样，判据也一模一样：
**没加载过 ⇒ 一定没在跑/没在识别**。

- `bus/ctrl`：`monmod(load)` + `EMPTY_MON` 空壳。`status()` / `is_busy()` / `stop_sniff()` /
  `switch_mode` 里的"问一句"全走不加载的路；只有真进 `sniff` 档才 `monmod(true)`。
- `svc/cmd`：`blocked_while_detecting`、`W:SALIAS` 更新推断行、`R:AUTODETECT`（没 sniff 时
  直接如实回 `not in sniff mode`）都不加载；`R:INFER` / `R:FRAMES` / `W:INFERWATCH`
  这类嗅探面板才加载。
- `iot/iot`：`trim_reqs`、`census`、发布循环里的 `infer_watch`、拓扑增量都改成
  "已加载才用"，没加载就按空处理（manual 档本来也没有推断数据）。
- `main.lua`：不再无条件 require，只在**开机直进 sniff** 时补加载 + 打日志。

前端不用改：`R:MODE` 里 `mon` 字段仍然是完整结构（空壳字段名与 `mon.status()` 一致），
`st.mon || {}` 的老代码照常工作。

回归测试：`tests/lua/test_mon_lazy.lua`（28 个检查点）钉住
①加载 `svc/cmd` + `bus/ctrl` 后 mon 未被加载；②`R:MODE`/`status()`/`is_busy()` 不加载且给空壳；
③`switch_mode(manual/idle)` 不加载；④`R:AUTODETECT` 不加载；
⑤`W:INFERWATCH`/`R:FRAMES`/`switch_mode(sniff)` 必须加载且照常工作。
Lua 30/30、前端 60/60、语法 21 文件 0 失败、模拟器 16 PASS / 5 SKIP / 0 FAIL。

**待真机复测**（烧下一版后按这个顺序跑）：

| 步骤 | 期望 |
| --- | --- |
| 开机 idle `R:MEM` | ~~从 273K 降到 ~250K~~ 见 11-20 实测：**不成立**，只省了 ~0.5KB |
| 进 manual `R:MEM` | ~~从 287K 降到 ~264K~~ 同上 |
| `--sizes 60` 单跑 | 保存 OK、读回 60 行（余量 ≥ 8KB） |
| `--sizes 16,24,32,48,60` 连测 | 32/48 至少过，60 看余量 |
| 进 sniff `R:MODE` | `mon.running=true`，`R:FRAMES` 有数据（嗅探没做瘸） |

> 如果 60 点仍差几 KB，下一步才是"寄存器行改定长数组"（330B → ~100B）
> —— 那一步要动 cfg/poll/collector/iot 约 80 处字段访问，风险比这步高一个量级，
> 所以先量这一版。

### 2026-11-20：惰性 mon 真机复测 —— 省了 0.5KB，不是 23KB（原判断错了）

烧 `9319273` 后实测，**"摘掉 bus/mon = 省 23KB"是错的**，原因值得记下来：

| 动作 | `R:MEM`（Lua 池 307192） | 差值 |
| --- | --- | --- |
| 开机 idle（mon 未加载） | 271520 | — |
| `W:MODE=sniff`（这时才 `require bus/mon`） | 272088 | **+568B** |
| 回 idle | 270512 | — |
| `W:MODE=manual`（require `bus/poll` + `data/collector`） | 277680 | **+7168B** |

结论：**Lua 脚本不是"require 才占池"**。开机时整个脚本区已经在池里
（225.7KB 瘦身源码 ≈ 271K 池水位 − 46K 运行态，正好对上），
`require` 只是把它挂进 `package.loaded` 并建模块表，增量只有几百字节。
所以"mon 23.3KB 源码 = 23KB 常驻"这条推论是错的（`bus/poll` 那 7KB 里大头
是 collector 模块 + 运行态表，也不是源码体积）。

惰性加载本身没错（少一个模块表、sniff 档之外不建 mon 的常驻状态），
但它**买不到 23KB**，60 点的账要另算。

#### 60 点到底差在哪：两个真账本

1. **每行 ~350B**（不是 330B）：`{addr,count,dtype,name,alias}` 五个字符串键
   = 表头 56B + 8 个哈希槽 × 24B = 248B，再加 name/alias 两条串。
   60 行 ≈ 21KB —— 只这一项就吃掉上传时能腾出的全部余量。
2. **MQTT 试连的 ±10KB 抖动**：4G 通、平台连不上时（现场无卡/无平台），
   每 30~60 秒试一次连接，一次占 ~10KB Lua + 30KB sys，失败再还回来。
   真机空闲水位因此在 **279K ↔ 289.5K** 之间来回跳（`sys` 66K ↔ 98K 同步跳）。
   上传正好撞进高点，就凭空少 10KB。

`9319273` 的 60 点复测（`mem_scale_e2e.js --sizes 60`，干净现场）：

```
[N=60] FAIL  rows=60  读回=0  Lua=289232/307192 (94%)  max=4096
        保存失败：第 4/5 片没有送达：设备返回失败：rx 丢弃, 请重发
```

死的不是"总共存不下"，而是**收第 4 片时取不出行**（`rx 丢弃` = prov 取行
分配失败/连败两次），当时已攒 48 行哈希行 ≈ 17KB + 解码临时 ≈ 4KB。

#### 这一版改了什么（A1）

1. **紧凑寄存器行**（`cfg.lua`）：行改成定长数组
   `{addr,count,dtype,name,alias[,off]}`，表头 56B + 5 槽 × 8B = 96B，
   加两条串 ≈ **165B/行**（60 行 21KB → 10KB）。
   靠 `__index`/`__newindex` 映射槽号，**所有读侧代码一个字没改**
   （`r.addr` / `r.name` 照写），只有构造口和编码出口要过 `cfg.row()` /
   `cfg.row_out()`：
   - `W:CSHARD` 收一片就折一片（`cfg.row_norm`），不再攒 60 行哈希行；
   - 读盘 `shards_load` 解一段折一段（`compact = true` 只给 poll/pull，
     infer 行是另一副样子，不走紧凑行）；
   - 编码出口 `shards_save` + `R:CFG`/`R:REG` 流式应答全部 `row_out()`
     —— 不然 `json.encode(紧凑行)` 会把它编成数组。
2. **块内偏移不再单独建表**（`bus/poll.lua`）：`{r=行, off=n}` 改成把 `off`
   挂到行第 6 槽，plan 里直接放行 → 每点省 64B，60 点省 3.8KB。
3. **上传期间关掉 MQTT 试连**（`iot.hold` + `W:CBEGIN`/`up_reset`/`hold_restore`）：
   闸门只挡"没连上时的试连"，已经连上的连接不动；上传/落盘一结束就放开。

回归：新增 `tests/lua/test_cfg_compact.lua`（把"落盘必须是对象不是数组"、
"读回逐字段一致"、"旧格式收得住"钉住），Lua **31/31**、前端 60/60、
模拟器 16 PASS / 5 SKIP / 0 FAIL。

**这一版第一次真机复测（`e826aa6` 烧录后）—— 还是没过，但卡点挪了**：

```
[N=60] FAIL  rows=60  读回=0  Lua=291840/307192 (95%)  max=6144
       保存失败：第 3/5 片没有送达：设备返回失败：rx 丢弃, 请重发
```

分片探针（`vkbox_shard_probe.js --n 60 --shard 1200`，每片之间 `W:GC`）看得更清楚：

```
[before]  lua 291736  sys 98K        ← CBEGIN 时正好有一条 MQTT 试连在飞
[shard 1] lua 295768  sys 66K (试连死了)
[shard 2] lua 288120                 ← 33 行紧凑行 ≈ +7.1K（旧版这里要 +11.6K）
[shard 3] lua 290904
[shard 4] lua 292832  max 2048       ← 60 行 ≈ +11.8K
[CFINISH] ERR 设备返回失败：not enough memory
```

三条结论，都是这一轮才量出来的：

1. **紧凑行是有效的，但 197B/行不是 165B**：60 行 11.8K（原来 21K）。
   name/alias 两条串按 ~35B/行算比估的高一点。
2. **`iot.hold` 只挡"新的试连"挡不住"正在飞的"**：`[before]` 那 291.7K 就是
   一条已发出的试连占着 10K。更要命的是**连接态的 client 本身也常驻 ~10K Lua**
   —— 真实部署（有卡、平台连得上）的基线本来就是 291K，不是 281K。
   所以 `hold(true)` 改成**连已连的 client 一起收掉**（`destroy_client()`），
   保存这几秒平台掉线，上报数据在 `pubsched` 里排着不会丢，`hold(false)` 自己连回来。
   调用点也挪到 `make_room()` **之前**，让双 GC 顺手把 client 的垃圾收走。
3. **卡点前移到 `CFINISH` 的写盘**：`shards_save` 原来按段攒**普通对象**
   （16 行 × 350B ≈ 5.6KB 临时表），再 `json.encode` 一次整段 —— 在 292.8K
   水位、最大连续块 2048 时正是"写盘前连续块不够"。
   现在逐行 `json.encode` **只留编码后的串**（~70B/行），封段时
   `"[" .. table.concat(parts, ",") .. "]"` 拼成一个段串，`kv_set` 写完立刻丢。
   峰值从 ~7KB 降到 ~2.5KB，`ensure_block` 也改成按**实际段宽**预检。

**这一版（A2）的真机验收顺序**：

| 步骤 | 期望 |
| --- | --- |
| 烧完先**断电重插**再测 | 清掉上一轮残留（实测用过一轮后 idle 会涨 4K） |
| `R:SN` | `VL20061117001`（烧录清了 fskv 就重写） |
| 开机 idle `R:MEM` | ~270K |
| `--sizes 60` 单跑 | 保存 OK、读回 60 行、`W:CFG 峰值` ≤ 96% |
| `--sizes 16,24,32,48,60` 连测 | 全过；60 的 `max` 不应掉到 1024 以下 |
| 保存后 `R:REG` | 60 行 JSON 对象（不是 `[100,1,...]` 数组） |
| 进 sniff `R:MODE` + `R:FRAMES` | `mon.running=true`、帧数在涨 |

> 如果 60 点还差，下一步不是继续抠行，而是**发布 MQTT 的 U4 分组**
> （60 点一份 JSON ≈ 5.4KB，96% 水位下拿不到这么大的连续块），
> 以及 `R:VAL` 的 `snapshot()`（每次新建 60 行表 ≈ 11K）——
> 那是"能采不能报/界面刷不出值"的另一道墙。

### 2026-11-21：CFINISH 炸在 `luaL_Buffer`，不是"总内存不够"

A2（`98ab055`）烧进去后 60 点的死法又变了，这次信息量最大：

```
[CBEGIN]  used 281712  max 6144      ← hold(true) 生效，开场没有那 10K 抖动
[shard 4] used 293464  max 2048
[CFINISH] RET:FAIL:CFINISH=not enough memory for buffer allocation
[R:CTRACE] enter 294416 / norm 295848 / freed 293696   ← 没有 saved 段
```

三个判读：

1. 应答是 `RET:FAIL:CFINISH=...`（不是 `RET:FAIL:CFG:...`），而且**没有**我们自己的
   `分片i/n写入失败` 前缀 —— 说明不是 `shards_save` 返回的错误，是某处 **raise**
   被命令分发器兜住、当成错误串回了。
2. 那句话不是 Lua 的 `not enough memory`，是 LuatOS 改写过的 `luaL_Buffer`
   扩容失败（`luaL_prepbuffsize` → `not enough memory for buffer allocation`，
   在 PC 模拟器的 Lua 核心里能直接搜到这句）。
3. A2 里唯一一处 **没 pcall、又用 luaL_Buffer** 的地方，就是 `shards_save`
   封段的 `table.concat(cur, ",")`。

为什么 1.2KB 的段会失败：LuatOS 的 `luaL_Buffer` 按 2 的幂扩 userdata ——
拼 1.2KB 依次要 256 / 512 / 1024 / **2048** 的连续块，而现场最大连续块正好
只剩 2048，最后一步就要不上。（同理 `string.rep` 探针在 n 略大于 1KB 时
也会去要 2KB —— 这一条顺带解释了以前"预检说够、真写不够"的怪事。）

改法（A3，`1a2272d`）：

- 封段改成 `..` 折（`join_parts`）：每次只分配"当前长度 + 新行"，峰值就是一个段宽；
- `SHARD_ROWS 16 → 8`、`SHARD_MAX 1024 → 640`：段 ~560B，`string.rep` 探针最多
  要 1KB，离天花板远一档；60 点 = 8 段，fskv 键完全够用；
- `W:CSHARD` 每收一片 `collectgarbage("collect")`，`W:CFINISH` 提交前再收两轮
  （那 60 张解码哈希行刚死，不收就是顶着垃圾写盘）；
- `save_json` 分片写遇 `memory` / `连续块` 类失败**收垃圾重试一次** —— 分片写幂等：
  预检失败一个字节没动，中途失败只是 header 停在 `st=w`，重跑一遍就齐。

**A3 的真机验收顺序**（断电重插建议保留，但不是硬要求）：

| 步骤 | 期望 |
| --- | --- |
| `--sizes 60` 单跑 | 保存 OK、读回 60 行 |
| `R:CTRACE` | 出现 `saved` / `done` 段（不再停在 freed 之后） |
| `--sizes 16,24,32,48,60` 连测 | 全过 |
| 保存后 `R:REG` | 60 行 JSON 对象（不是数组） |
| `R:MODE=sniff` + `R:FRAMES` | `mon.running=true`、帧数在涨 |
